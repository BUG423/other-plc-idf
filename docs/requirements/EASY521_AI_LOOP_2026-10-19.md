# Easy521：Linux 终端 AI 编程与现场反馈闭环需求

日期：2026-10-19。状态：需求基线；本文件记录当前软件边界与待验收目标，不代表新的真机测试结果。

## 用户要完成的事

用户在现有 Linux/WSL 终端中描述控制需求，AI 维护可阅读、注释完整的 ST，完成检查、编译、下装，取得运行数据及用户现场观察，再据此修改下一版。每轮都能回答：改了什么、编译了什么、给哪台设备做了什么、哪些结果实测过、哪些仍未知。

第一台验收设备按现有 Easy521 工程处理；用户口述型号有差异时，以新鲜设备身份记录核对。后续扩展其他 PLC 采用目标后端和板级配置，不假设芯片、ABI、通信协议或系统固件通用。

本需求细化既有 [SPEC](SPEC.md)、[PLAN](../management/PLAN.md) 及 [多目标决策](../architecture/ADR-0002-native-multitarget.md)。这些文件包含早期阶段快照；下述“当前能力”以本轮读取的源码和带日期证据为准。

## 交付层级

| 层级 | 用户能做什么 | 完成判据 |
|---|---|---|
| 过渡闭环：WSL 调用 Windows | 终端生成/修改 ST，调用厂商编译及既有工程下装，收集数据和人工反馈 | Easy521 的两次不同程序行为均有设备与程序身份关联；明确保留 Windows 依赖 |
| 最终闭环：严格 Linux 原生 | 编译、链接/包装、传输、运行控制与监测均由 Linux 工具完成 | 关闭 Windows 后端仍能对同一 Easy521 完成上述闭环；保存进程、依赖及设备证据 |
| 可复用目标框架 | 同一工程与反馈流程接入其他设备 | 每个型号分别声明编译、产物、部署、运行及 I/O 能力，逐项验收 |

“无 GUI”只说明不需要界面操作。Linux 发起 Windows `StLang` 仍属于过渡方案。`open-linux` 的 MatIEC/GCC、扫描与确定性 replay 是已实现的 Linux 执行目标，可验证有限 ST 行为；它没有证明其产物能在 Easy521 上运行。

## 四层操作不能相互替代

| 层级 | 对象与预期 | 已知路线与边界 |
|---|---|---|
| 应用参数/命令 | 改运行中应用约定的设定值、启动请求等 | Modbus/FINS/OPC UA 需端点、地址或公开变量和应用语义；写 D 区不等于 CPU 执行了新 ST |
| CPU 模式 | 查询或请求 RUN/STOP，确认实际状态 | 需要该型号已校准的状态与命令接口；M8000/M8001 状态位不能当作可写模式命令 |
| 新应用 | 编译新的 ST、绑定全局/库/任务/I/O，链接包装并下装 | Windows 原生工程路径已有部分真机证据；独立 ARM `.o` 仍缺完整应用链接、包装与设备绑定 |
| 系统固件 | 替换启动链、系统或 PLC runtime | 需要芯片/存储布局/BSP/驱动/恢复路径等独立证据；不属于应用闭环的必要前提 |

最短路线按实际需求选择：已有应用定义好命令寄存器时，Linux 参数控制有用；要求 AI 改任意控制逻辑时，必须走新应用路线。不能以参数写入成功替代程序下装，也不能为了应用开发默认转入系统固件替换。官方通信限制见 [手册核查](../research/firmware/13-documented-control-routes-2026-10-18.md)。

## 功能与证据要求

| ID | 要求 | 可验收结果 |
|---|---|---|
| EAI-R01 | 复用用户现有 AI 终端，需求转成有限、可检查的控制规则 | 保存需求版本、单位/范围、启停/故障/复位/重启约定及未决问题；不另建聊天服务 |
| EAI-R02 | AI 生成适合既有厂商工程的 ST | MAIN 正文不混入 `PROGRAM/CONFIGURATION`；现有变量接口、任务周期和物理绑定不被隐式更改 |
| EAI-R03 | 编译结果可追溯，语法错误能失败 | 原始源码哈希、完整工程输入、编译诊断与产物清单关联；错误 ST 不产生“已部署成功” |
| EAI-R04 | 一次下装绑定选择的候选 | 关联 build、intent、release、operation；项目比较与端侧字节绑定分级报告；超时/漂移为 unknown，不自动重放 |
| EAI-R05 | 运行与停止可核实 | 同一设备、同一候选的计数/心跳或需求信号有连续样本；CPU 状态取自已校准接口，停止后状态与样本时间可解释 |
| EAI-R06 | 人工观察作为一等反馈输入 | 记录版本、动作、期望、实际、时间、来源及 unknown；能表达“未看到/未测/不确定”，并引用原始照片或日志哈希 |
| EAI-R07 | AI 根据证据修改下一版 | 下一轮关联父轮和需求版本；说明改变的规则；保留失败样本和原验收，不为通过测试静默放宽期望 |
| EAI-R08 | Linux 原生依赖可核实 | 完整应用编译/部署/监测过程没有 Windows 进程或服务参与；独立记录工具版本、许可证、输入及输出哈希 |
| EAI-R09 | 输出便于 AI 与人理解 | JSON 区分 preview/failed/unknown/verified 和验证层级；给出具体缺失条件，不用软件通过数代替真机结果 |

部署操作沿用现有会话授权和默认预览语义；反馈文件本身不是授权凭据。设备动作由当前目标后端执行，不把历史 USB 位置、IP、型号、固件或供电描述当作当前事实。

## ST 编写标准

以下是本项目的工程约定，目标是易审查和可维护，不宣称满足某项功能安全认证。

1. 文件说明写明用途、需求版本、目标/既有变量接口、单位、有效范围、扫描周期假设、复位与重启行为、已知限制。运行时变量记录程序版本或探针规则时，明确它只能辅助辨识行为，不能独立证明设备二进制身份。
2. 注释解释控制原因、状态转换、优先级和边界；时间与阈值用有单位的含义表述。修改规则时同步修改注释，避免逐行复述赋值。
3. 使用明确类型、范围和命名；避免隐式窄化、无界循环、等待式阻塞。输出写入点、启动边沿、定时器复位和故障处理保持可追踪。
4. 停止、许可丢失、故障、复位的优先级来自需求。需求未说明时标为未决，不能由 AI 擅自认定一种行为已被用户要求。
5. 现有厂商 MAIN 只接收正文。新增全局变量、库、任务、周期或 I/O 绑定属于显式工程变更，不能用正文声明偷换已有接口。
6. 按需求覆盖正常、边界、启停、复位、故障、许可和数值范围。`open-linux` 场景只验证其运行时支持的语义；厂商编译和真机扫描仍需分别验收。

## 每轮记录与人工反馈

每轮分配 `iteration_id`，保存父轮、需求版本、原始 MAIN 的 `source_sha256`，并引用既有 verified build、`intent_hash`、`release_hash` 和动作记录。完整工程的 `source.tree_sha256` 与单一 MAIN 哈希含义不同，两者都保留；不能互相替换。

设备记录应包括本次观测到的型号、固件、可用的唯一身份及连接位置。IP、USB busid、VID/PID 是连接线索，不能单独当作永久设备身份或程序身份。端侧二进制尚未读回时，其哈希保留 null，绑定等级明确为 unverified/unknown。

人工反馈采用 [最小记录 schema](../../examples/easy521_feedback/feedback.schema.json) 和 [未知结果示例](../../examples/easy521_feedback/unknown-feedback.json)。这是一份观察记录，不是第二套工程配置；继续复用现有 `plcidf.json`、`.plcidf.toml`、构建/部署记录及证据引用。实际动作、预期与实际分开，原始证据用 `path/sha256/source` 引用。AI 推断不得伪装成人工现场观察；schema 校验只能验证记录形状，不能验证内容真实性或执行任何命令。

采集工具需启用 `date-time` 格式断言，检查带时区的真实日期，不能只加载 schema 而忽略格式。示例的 `record_kind=example` 必须保留为示例，实际报告另建 `observation` 记录；无法关联程序身份的现场观察仍可保存，但不能据此提升整轮验收等级。

| 完整输入与本地候选 | 2026-10-18 完整输入覆盖及确认前 release 捕获/复核 | 候选确认后确被传输并执行；[本地验收](../../evidence/easy521-application-20261018/complete-local-release-root-acceptance.json) 明确没有下载确认 |
| 独立正文编译 | [受限正文与显式全局到 ARM 对象](../research/firmware/11-plain-main-object-2026-10-18.md)，真实 +1/+2 与语法负例 | 完整应用链接、任务/I/O 绑定、包装、独立下装；当前仍依赖 Windows 编译器 |
| 运行控制与监测 | `open-linux` 有真实 run/stop/replay；Easy `vendor-usb` 能读当前可见表格值 | Easy CLI `run/stop/verify` 尚未提供；UI 值本身不能证明当前在线、CPU 扫描或目标程序身份 |
| Linux D 区客户端 | 一次 FC06 写及同连接 FC03 读回、超时不重放的回环测试 | 当前 Easy521 端点、映射、权限与应用效果；工具尚未用于本轮真机 |
| 自动化检查 | 历史 879 项软件检查及另批 150 项软件/回环检查 | 两组检查均不是 PLC 真机运行证明，不相加包装成硬件验收 |

当前 CLI 事实见 [使用说明](../EASY521_CLI.md)：Easy `build --source --build-record` 和 `flash --build-record --backup-record --field-facts` 已有路由；`--manifest` 仍是原始构建清单。`monitor --transport vendor-usb` 明确保留未核验结果。`run/stop/verify` 目前仅限 `open-linux`。

主电源额定值、USB 下载能力与 CPU 能否运行是不同问题。过去 USB 连接下 RUN 失败和手册额定 24V 不能单独证明因果关系；本次供电、开关、诊断、负载和 CPU 状态需要新鲜观测，不新增“没有 24V 必须禁止 RUN”的软件结论。

## 完成验收

先在既有内存探针范围完成两轮：规则 +1、规则 +2 各有独立源码与候选身份，设备反馈能区分两轮；执行状态和停止后的变化得到校准确认；故意错误 ST 被编译拒绝且不会冒充新应用成功。人工反馈及运行数据引用同一轮动作和时间窗口，下一轮保留原始失败信息。

若端侧二进制绑定暂不可得，结果必须标明 project/runtime 的实际证据等级，不能宣布严格端到端身份验收已完成。对涉及物理输出的用户需求，应另加现场可观察的验收项，不能用内存探针替代。严格 Linux 原生终态再独立验收，不能由过渡闭环自动升级。

实施任务见 [本轮任务分解](../management/EASY521_AI_TASKS_2026-10-19.md)，架构取舍见 [ADR-0005](../architecture/ADR-0005-easy521-ai-control-loop.md)。
