# PLC-IDF 实施计划与验收基线

日期：2026-10-17。适用目标：汇川 Easy521-0808TN；以仓库证据为基线，硬件型号、固件和 AutoShop 版本须在每次联调时重新核对。

## 1. 产品需求与范围

将用户所说的“CVI”暂按 **WSL 中的 AI 命令行开发环境**理解。需要交付的产品是 AI 和人都能调用的 PLC 工具链：需求和验收场景 → 文本工程 → 检查 → 编译诊断与产物 → 指定设备下载 → 运行反馈 → 修改。CLI 必须能判断每一步是否实际完成，并把反馈交回 AI。

第一阶段默认接受 Windows 后台执行 AutoShop，用户的日常入口留在 WSL。完全去 Windows 是另一项可独立验收的目标；如用户将它定为第一阶段硬约束，则桥接路线只作参考，必须先验证原生后端或更换开放目标平台的可行性。

AI 对话由现有编码代理承担，PLC-IDF 首期提供工具接口、工程契约和反馈，不自建聊天产品。ST 是首期选用的文本语言，现有 Python 是上位机、算法参考和编排工具；项目名称不意味着已经支持 Python 直接编译到 Easy521。

### 可验收需求

| 编号 | 用户需要的结果 | 通过条件 | 实施任务 |
|---|---|---|---|
| RQ-01 | AI 能独立读写工程 | manifest 固定型号、方言、工具版本、任务周期、I/O/寄存器映射；示例能从空目录生成并检查 | T04 |
| RQ-02 | 修改能进入厂商工程 | 同步前有 diff；在工作副本上同步，结果能追溯到源文件哈希；原工程可恢复 | T06 |
| RQ-03 | 编译反馈可信 | 有效/故意错误源代码都正确判定；诊断可机读；产物包含哈希和源版本；仅 GUI rc=0 不算通过 | T02、T05、T06 |
| RQ-04 | 下载到指定设备 | 下载计划绑定产物与设备身份；并发拒绝；下载结果经厂商程序校验；未知状态不得算成功 | T07、T09 |
| RQ-05 | 运行结果回流 | 原始寄存器、解析值、时间、质量、工程/契约版本可回溯；断连、字序不明与陈旧数据可区分 | T08 |
| RQ-06 | 能在没有 PLC 时开发 | 干净 Linux 安装后可运行监测软件闭环；场景播放器明确标示不执行用户 ST | T03、T04 |
| RQ-07 | 面向 AI 稳定调用 | stdout 为版本化 JSON，进度在 stderr；明确退出码、超时和可用能力；不依赖 TTY | T05 |
| RQ-08 | 逐步移除 Windows 依赖 | 分别证明编译、打包、下载、观测哪层可替换；不能把 ARM/Linux 识别当作兼容性验收 | R01、R02 |
| RQ-09 | 工作进展可审阅 | GitHub 任务含依赖、验收、证据和负责人角色；完成结论经复核；定期汇总不冒充新测试结果 | T01、进展工作流 |

### 非功能要求

- 可复现：锁定已验收的编译器、AutoShop、固件、寄存器契约和 Python 依赖版本，记录源码与产物哈希。专有编译器不能保证二进制完全一致时明确记录其变化来源。
- 可靠性：所有外部操作有超时；状态变化操作不盲目重试；有副作用但结果不明时要求先核对现场状态。
- 可观测性：构建、下载、运行分别给出验证等级，保留原始输出和证据引用。文件更新时间本身不证明本次编译成功。
- 操作边界：本轮仅软件修改、文档/离线研究和 GitHub 同步；没有授权本轮下载、RUN/STOP、固件升级或调试口操作。已有真实工程和历史证据保留。
- 可维护性：CLI 不直接依赖某一个 GUI 流程；按实际能力选择后端，支持只读监测独立安装和运行。

## 2. 架构决策

```text
现有 AI 编码代理 / 人
          │ 文件 + plcidf CLI（JSON / 稳定退出码）
          ▼
项目模型（ST / 变量 / 任务周期 / I/O / manifest）
          │
          ▼
检查与编排 ── 源版本/产物清单 ── 部署计划/证据
    │                 │                 │
 BuildBackend     FlashBackend     MonitorBackend
    │                 │                 │
 Windows AutoShop 桥接              Linux Modbus
    │                 │                 │
    └────────── 厂商 PLC runtime / 设备 ──┘

横向：环境诊断、设备租约、版本能力矩阵、超时、审计
研究：原生厂商编译/下载适配；开放 PLC 后端；底层固件
```

1. `build`、`flash`、`monitor` 分开验收。下载用户应用与替换系统固件是不同操作、不同产物、不同恢复路径。
2. 当前仅 `build/flash/monitor/sim/devices` 为已存在命令。`init/check/sync/doctor`、注册式后端、产物清单与设备租约均是计划，不作为已实现 API。
3. 桥接是第一阶段实现选择。初期 GUI 自动化需要 Windows 交互桌面；“用户不手动点窗口”不等于“真正无头运行”，服务化前须单独验证 DLL/官方自动化接口。
4. 当前仿真是固定 BESS 场景播放器。它验证数据链，不能证明新生成的 ST 逻辑、PLC 周期和真实 I/O 正确。
5. 当前 Modbus 监测为寄存器数据采集。通用变量浏览、断点、单步、任务时序、故障诊断应逐项列能力，不能以 `monitor` 一个名字视作全部具备。
6. 原生编译须同时验证方言、runtime ABI、链接/重定位、程序包装与型号兼容；原生下载另需会话/校验/错误恢复协议。研究结论见 [固件评估](../research/firmware/03-feasibility-assessment-2026-10-17.md)。

与 ESP-IDF 的对标以项目模板、配置、依赖版本、编译诊断、产物追溯、目标选择、下载校验、监测和 CI 为准，而不是仅复用三个命令名字。[ESP-IDF 官方 CLI 文档](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/tools/idf-py.html)用于能力对照。

## 3. 工作分解与依赖

详细验收条目以 [tasks.json](tasks.json) 和对应 GitHub Issue 为准；估算为完成前置条件后的工程工作日范围，不是日历承诺，也不代表已经招募了相应人员。

| 任务 | 优先级 | 技术执行角色 | 依赖 | 交付/验收重点 | 工作量估算 |
|---|---|---|---|---|---|
| T01 基线与规划 | P0 | 架构代理 + 统筹复核 | 无 | 实现、设计和证据分层；任务、研究和状态可追溯 | 本轮 |
| T02 执行结果语义修复 | P0 | Python 实现代理 + 统筹复核 | 无 | 非布尔值不能授权；GUI 不自动重试；未校验不能报成功 | 本轮 |
| T03 独立安装与 CI | P1 | Python 构建工程角色 | T02 | wheel 从仓库外运行；依赖/资源齐全；软件测试隔离硬件 | 1–3 日 |
| T04 文本工程与检查 | P1 | PLC 语言/工程模型角色 | T01 | manifest、模板、ST/变量/映射检查和行级错误 | 2–4 日 |
| T05 能力诊断与机读协议 | P1 | CLI/接口工程角色 | T02、T04 | 分后端能力、JSON schema、退出码、环境诊断 | 2–3 日 |
| T06 同步与可验证编译 | P1 | Windows 自动化 + PLC 工具链角色 | T04、T05 | 工作副本、diff、真实正确/错误编译、产物清单 | 3–6 日 |
| T07 部署契约与设备互斥 | P0 | 系统/部署工程角色 | T02、T05 | 严格设备身份、产物/计划绑定、租约、证据失败即停 | 2–4 日 |
| T08 真机只读监测 | P1 | 通信/测试工程角色 + 用户现场 | T05、网络可达 | 已知值对照、字序不明处理、数据质量、断连和契约版本 | 1–3 日 |
| T09 应用下载与运行验收 | P1 | PLC 联调/测试角色 + 用户现场 | T06、T07、T08 | 有人在场下载；厂商一致性校验；RUN/STOP 与周期有独立证据 | 1–3 日 |
| R01 原生编译与下载研究 | 研究 | ABI/协议研究角色 | 离线样本；抓包另需现场 | 工具/ABI/协议各自可行性，最小原型与退出门槛 | 首轮 3–5 日 |
| R02 系统固件与开放平台研究 | 研究 | 嵌入式 Linux/实时系统角色 | 官方镜像/硬件资料 | 来源、哈希、分区/SoC/runtime/I/O；开放平台演示与移植成本对比 | 首轮 3–5 日 |

建议顺序：T02 → T03/T04 → T05 → T06 与 T07；T08 在网口条件具备后并行；T09 为主线最后一道验收。R01/R02 设时间盒并行，不阻塞桥接主线。

研究退出条件：首轮未取得可验证 ABI/官方接口/有效下载协议，记录尚未解决的具体问题后保留桥接；镜像中缺 I/O、现场总线驱动或恢复路径时，不把替换固件列入现有 Easy521 的产品交付。开放平台 runtime 原型不能称作 Easy521 兼容实现。

## 4. 里程碑与完成定义

| 里程碑 | 包含任务 | 完成证据 |
|---|---|---|
| M0 事实与可信状态 | T01、T02 | 审计、基线回归、修复负向测试、GitHub 任务与报告 |
| M1 可安装的工程前端 | T03、T04、T05 | 干净环境安装、模板与坏输入检查、JSON 契约与 CI |
| M2 可验证 Windows 桥接 | T06、T07 | 正/负编译、源到产物追溯、部署计划/互斥负向用例 |
| M3 实验机全闭环 | T08、T09 | 真机只读已知值、授权下载、一致性校验、运行与周期记录 |
| RX 原生能力路线选择 | R01、R02 | 带样本哈希、复现步骤和限制的研究结论；是否投入原型的决定 |

所有任务须同时满足：交付可审阅、验收有证据、失败路径可解释、无未注明的硬件假设、任务依赖已满足，才可关闭。研究任务以回答问题和记录否决证据完成，不以“成功绕过厂商”作为预设结论。

## 5. 分工与汇报

本轮由三个 AI 技术执行代理完成架构审计、实现与质量验证、固件公开/离线研究；统筹代理负责交叉复核、修复范围、依赖、GitHub 与报告。这是技术角色分工，尚未联系或雇用真实企业人员。后续工程角色由下一轮执行代理或用户指定的工程人员承担；GitHub Issue 中的“责任角色”不代表已有人接单。

每个工作包开始时确定输入与验收；执行中在当前对话持续报告；完成后记录变更、测试、限制和下一步，再更新 GitHub Issue 与 [PROGRESS.md](PROGRESS.md)。

本轮默认提供里程碑更新及每周一 09:00（Asia/Shanghai）的 GitHub 任务状态汇总。GitHub Actions 仅统计任务，不会离线继续研发、运行 PLC 或自动宣称测试通过；工作流需进入默认分支后才启用，具体启用状态记在 PROGRESS。后续频率可按用户回复调整。
