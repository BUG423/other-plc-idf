## 失败和传输边界

1. 首次小文件 `userprog.foid` 读取成功，前后 GCM raw1。
2. 全集尝试在 `project.hcpp` 的只读打开收到 op15/error132 后立即停止。错误语义尚未确认，没有猜路径、前缀或改名重试，因而没有源码归档备份成功声明。
3. 首次大文件读取收到首块正确 512 字节回复，下一块请求收到 rc0/0B 后停止，保留 unknown，没有重发 OUT。
4. 修复代码后建立新的显式实验。先仅接收至多三个待收 USB transfer，没有发送 OUT，取得与前次未完成 block1 对应的 512 字节帧、零长度包及最后一个有界接收超时；原失败记录保留。随后才进行新的读取计划。

新实现仅在**同一句柄内**前一成功回复恰为 512 字节时，允许下一回复前消费一个零长度包，仍使用原接收截止时间与四次 IN 上限；没有依据的零长度、重复空包或数据中途空包仍拒绝。完整 17 文件计划取得 299 个关联回复，记录 265 个符合此条件的零长度包。这里的继续 IN 是接收同一请求的回复，没有额外 OUT、重连重放或 PLC 写命令。具体包分布在元数据中保留。

## 主机准备与尚未完成的验收

每次实验均由统筹独占设备，在新鲜 USB 身份核对和空闲串口检查后，临时授予普通用户节点访问权并只解绑本设备 CDC 控制接口。实际读回进程为普通用户 Python/libusb，审计钩子禁止 Python 子进程与 socket 回退；主机准备使用 WSL root 启动器，USB 附加此前由 Windows usbipd 完成。这不等于整台 Windows 宿主已完全断开。

四次实验的 finally 均记录控制/数据驱动与原节点属主、权限恢复成功。设备端文件 route 的最终清理没有独立读回证据，保持 unknown；没有发送猜测 close、reset 或状态恢复命令。

本地两份[带注释 ST 示例](../../../examples/easy521_native_memory/)已分别真实编译、链接、绑定并组装为 18 文件候选，源码和对象哈希列入汇总。这条本地构建链与上述设备旧应用的读回分别验收。当前仍未证明候选的完整符号元数据、设备接受、新 ARM 程序运行、STOP 后停止变化、修改规则后的第二轮行为，也未执行备份恢复演练。17 文件读回是后续核验与恢复设计的输入，不能称作已经验证可恢复的完整备份。
