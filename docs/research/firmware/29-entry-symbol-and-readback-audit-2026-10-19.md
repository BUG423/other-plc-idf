# 新 MAIN 入口、符号元数据与真实备份的独立离线审查

2026-10-19。本轮只在 Linux 读取统筹已经获取的设备备份、既有工程和原厂组件，没有执行 Windows/厂商 DLL/Simulator，没有设备或 Git 操作。主要依据为 `.plcidf/native-execution-backup-zlp-20261019T072754Z/` 的17项设备执行文件、研究27/28候选及本机原厂编译/模拟组件。逐字段来源、哈希和局部调用地址见[JSON](29-entry-symbol-and-readback-audit-2026-10-19.json)。报告27/28的历史候选保持原样。

**未发现 MAIN 函数长度变化导致 Output/ILIndex 或名称表中的代码偏移失效。真实备份与固定模板的指令、索引和变量分配内容相同，文件长度差来自压缩。symbol.sym 中的16字节字段已证实是厂商 ST 文本集 MD5，当前未重新生成；它不能冒充新源码的一致性证明。**所检查 Simulator 的装载路径不使用该 MD5 验证代码，但这不是对 Easy521 固件的验收。物理设备是否接受候选，仍需独立的文件校验与执行读回。

## 1. 215 字节 userprog 是压缩形态

设备回读 `userprog.foid` 为215字节，模板为294字节，均属于同一工程UUID。将设备文件严格按 LE DWORD tag/length 分段：

| tag | 设备 payload | 展开/作用 | 与模板比较 |
|---|---:|---|---|
| `0x100/0x200/0x201` | 4/32/4 B | 既有64字节封装头 | 相同 |
| `0x40000` | 34 B zlib | 56 B 指令数据 | 逐字等于 `Output.prg` |
| `0x40100` | 23 B zlib | 112 B 索引数据 | 逐字等于 `ILIndex.idx[30:]` |
| `0x40200` | 24 B | 六个LE DWORD：34、56、23、112、0、0 | 压缩/展开长度表 |
| `0x280` | 38 B | 工程UUID | 相同 |

因此215与294的文件哈希不同，不能直接解释为任务或逻辑内容不同。展开后56字节 SHA-256 为 `3bfe2324eba14f55199d5bb4d0ee72d265a7453fc78b0c6e66d265ae21adb63b`；112字节为 `ed8bb93782bf125bdfe0b7cd111d291d6f08ad07a5ce1382ff289f5e1dd0bbef`。

设备 `varsinfo.foid` 的173字节也不是变量丢失。模板使用 `0x30000/284` 原文；设备使用 `0x30001/34`，前两个 DWORD 为展开长度284和压缩长度26，其后26字节 zlib 展开后逐字等于 `VarsInfo.vi`，SHA-256 `9c7cab9b340bbc5e5a352caa6fa54c3c8514b0c259b9691908995ca48ea1df95`。UUID及尾部小记录均保持。统筹/配置线的后续候选应区分这两种已观察的包装，不把解析成功升级为任意固件均接受。

设备的12个配置文件与研究28模板相比，payload（偏移64起）和末DWORD（偏移60）全部逐字相同；每个文件仅不透明32字节头字段内的绝对偏移26、27不同。没有据此将其重命名为校验和或版本。研究30另行记录设备字节继承候选。

## 2. Output/ILIndex 不依赖 MAIN 的 ARM 长度

LAB 工程原厂 MAIN 函数为908字节，LED工程为108字节，新原生 REAL MAIN 为34字节。前两者的 `Output.prg`、`ILIndex.idx` 和未压缩 `userprog.foid` 逐字相同；当前设备回读展开后的这两段也相同。

这支持这些固定段是既有指令/任务入口包装，不是 MAIN ARM 机器码或代码大小表。它不单独证明实时任务已经调用新 MAIN；实际执行仍必须另测。

`symbol.sym` 的两个段各保留 `id=1 → MAIN`、`id=2 → SBR_001` 的名称记录；所观察的名称表和边界偏移在不同 MAIN 大小时保持。Simulator `CompileSystem.dll` 的 `symb_file_load_st_pou`（VA `0x6a74edbc`）读取id和名称，`sym_maps_from_module`（`0x6a74e664`）则遍历**当前 ELF**的 STT_FUNC 项，按符号名称与 `st_value` 设置函数体地址。它不从旧 symbol 文件取 MAIN 的 ARM 起止偏移或长度。这是名称绑定设计的交叉证据，不能当作真实固件源码。

## 3. symbol.sym 的变化字段及其来源

三个实际同接口工程的符号文件并不逐字相同：

| 来源 | 每段 `+26` DWORD | `+30..45` 16字节 | `+46` DWORD | `+50` WORD |
|---|---:|---|---:|---:|
| LAB模板 | 7 | `df6a8ca75fab7f0abdaa45ae40d66302` | 100 | 3 |
| 当前LED/设备 | 7 | `fae9727b679e9a2dbd0f0139153033f7` | 100 | 5 |
| 原BESS工程 | 7 | `4a2c93da2d891c070530ecf19bbafe06` | 101 | 5 |

本轮已追到来源，避免继续把这些值猜成代码长度：

- `H530Converter.dll 0x1016c588..0x1016c5fc` 分配20字节，通过 `CSTCompiler` 虚表 `+0x14/+0x18` 填充，再传入符号生成器。
- `STCompiler.dll` 的 RTTI 识别出 `CSTCompiler_HC`，虚表为 `0x100bcefc`。`+0x14=0x1003fc40` 将调用者提供的版本写成 LE DWORD；`+0x18=0x1003fc30` 转到对象内 `+0x5c4` 的文本集合与 `0x1009a8c0`。
- 后者对存储的名称/字节缓冲区集合执行 `g_MD5Init/Update/Final`，版本及字符串编码分支会影响输入。没有把它复原成“MD5(新ARM对象)”；此前对 MAIN.o、stprog.o、stuserprog.o、MAIN.ST、hcpp 的单文件 MD5 均不匹配。
- 符号生成器将上述20字节复制到每段 `+26..45`。精确的厂商前处理文本集合、顺序与全部名称来源还未完整重建，**本轮不生成或伪造新厂商 MD5**。
- `+46` 来自 `CompileCfg.ini` 的 `[Symbol] CustomFunc=100`，再加 converter对象 `+0xa4` 的计数。它不是 MAIN 机器码长度。
- `+50` 从创建调用栈参数 `+0x2c` 的低WORD，经 converter对象 `+0x64`、`0x10013bbb`、符号 writer 参数写入。其具体选项含义尚未恢复；没有擅自将3或5命名为编译器ABI版本，也不将它改成想要的值。

当前模板仍继承 LAB 元数据，新源码来源使用本项目 source→compiler→link→binding 哈希链表达。**不能声称厂商在线源代码 MD5 与新源码一致。**未来通用兼容实现仍应恢复该元数据；本轮未找到它构成当前物理装载必然阻断的证据。

## 4. Simulator 装载检查的证据范围

完整检查了 `CompileSystem.dll` 的以下函数：

- `symb_file_load`：读取整个符号文件。
- `st_loader_load_symb_file`（`0x6a74cb74`）：检查所选段头 `+8` 类型与装载器要求的1/2一致，建立 ST/LD POU 与命令名称表。
- `st_loader_load_elf_file`（`0x6a74cac4`）：装载 ELF、设置变量/函数解析回调，随后按新 ELF 符号填写 POU 函数地址。

在这些已检查路径中，没有用符号头 `+26..45` 的 MD5、`+50` WORD 或旧 MAIN 长度对代码作比较。该模拟组件中的 `elf_module_sig_check` 仅返回0，也不能推导真实固件没有其他校验。

实际操作的可用判断是：可以明确继承元数据，并以**设备回读文件哈希、目标身份、源构建链和新程序行为**作为独立实测判据；不能把旧MD5当成源一致，也不能仅凭模拟组件不存在某检查就保证真机接受。是否进行受控下装，由统筹结合已经保存的设备执行文件和当次状态决定，本代理未执行下装。

## 5. SBR 与初始化/隐藏约定

固定 `SBR_001.o` 的 SHA-256 为 `0427a175b83bd445b632a449e92fde9276b2a703737e7ceadaca08d4f1d6d411`。其唯一可执行 `.text` 为2字节，SBR_001仅执行 `bx lr`；没有文本重定位、调用、数据访存或物理输出操作。因此该既有 SBR 本身不执行 BESS 业务或 I/O。新 MAIN 自身只访问 Pcmd 变量；这不等于已验证整个 PLC 的所有任务、初始化和外部配置均无副作用。

旧原厂最小 DINT/REAL对象没有 `.init/.init_array/.ctors` 入口；MAIN不要求一个表达式之外的固定初始化调用。它们有264字节左右的编译器私有 BSS 暂存及异常/调试元数据。新 MAIN 不使用这些私有临时全局，未生成它们；复用 SBR/两库自己的 BSS与引用仍存在。新 `nounwind` MAIN 的 unwind记录与旧对象有区别；当前没有隐藏初始化节被遗漏的证据，但运行库、浮点状态和真实固件 ELF 装载仍属于真机ABI验收范围。

另：源码归档只读打开的错误132保留原事实。Simulator `_file_route_create` 在路径生成失败、读取前提失败和 fopen 失败等多个分支都返回 `0x84`；本轮未恢复真实设备该码的精确枚举，**不能据132断言文件不存在或推定应该换路径重试**。本轮没有追加路径尝试。
