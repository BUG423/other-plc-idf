# 39. Easy521 原生应用下装、STOP 读回与 RUN 故障记录（2026-10-19）

本次 Linux 原生链已经把候选的 **17 个应用/配置文件传到设备，并独立上传读回，逐字一致**。STOP 请求得到 ACK，随后独立 GCM 读回 raw0；RUN 请求同样得到 ACK，但随后 GCM 仍为 raw0，没有通过运行验收。用户随后报告 RUN 灯灭、ERR 红灯亮。后续状态、文件和错误数量读取分别超时；用户报告断开 24V 与 Type-C 后重接，ERR 仍红。

截至本报告所收录的 `2026-10-19 08:41:03 UTC`，**没有读到实际故障码，没有证明新 ST 已执行，也没有执行原始基线恢复**。冷启后的 Linux 文件通道和另一次 Windows 原厂 libusb0 固定 GCM 只读检查也未返回有效数据。研究40发现的外部变量对齐风险是离线定位线索，不能写成已经确认的唯一故障原因。本记录保留失败候选与历史会话，不用后续修正版替换这次事实。

## 对象与来源

目标是用户指定的 Easy521，现场最后确认输出端子悬空、未接外部负载；这是用户报告，没有进行电气测量。冷启前 USB 为 `001:002 / 0471:a531`，冷启后重新枚举为 `001:003 / 0471:a531`；两次描述符 `bcdDevice=784 (0x0310)`、无序列号。USB 描述符不能替代 CPU/应用身份认证，也不能当作已读到 CPU 固件版本。

本次实际下装的是 [conditional_plus1.st](../../../examples/easy521_native_memory/conditional_plus1.st)：既有 REAL `g_rBESS_Pcmd` 小于10时加1，否则置0。源码 SHA-256 为 `4f9dba05f28f5b3d300b752856d9e1648b308f26a7f99c2480abafa5e6d416f1`。实际 MatIEC → C → Clang ARM → 两级链接 → 既有变量绑定的候选 manifest SHA-256 为 `ce5f75a77680e25da792a9491b0b77c4504052f10cc02908e2537e4d7618cc33`。这里的 build 标识是该 manifest 的哈希，不是独立签名构建证明。`plus2` 没有在本记录中下装。

[公开摘要](../../../evidence/easy521-native-fault-20261019T083854Z/summary.json)分别保存机器观察、人工观察、11次会话中的61条观察及17项文件对照；[来源索引](39-native-download-fault-2026-10-19.json)给出私有证据路径、长度和哈希。私有报告可能包含厂商文件内容，因此没有原样公开。本文档整理没有访问设备、执行 Windows 工具或操作 Git；收录的 Windows 只读检查由统筹另行执行。

## ACK、状态与程序执行的边界

STOP 的局部应答为 `09000101cbae000006`；RUN 的局部应答为 `090001019760000006`。二者都是9字节、op6、无 DWORD 正文。它们说明请求获得关联应答，不提供应用运行结果。

STOP 后独立 GCM 回复为 `0b00010151b50000050000`；RUN 后独立 GCM 回复为 `0b0001016a5a0000050000`。两帧正文都是 `00`。厂商静态映射将 raw0 对应 STOP、raw1 对应 RUN；原始观察仍保留 `state_semantics=unknown`、`device_calibrated=false`，人工灯态单独记录。本文没有把 ACK、GCM、M8001 或人工观察互相替代。

故障后的 GCM、文件读取、错误数量读取以及冷启后错误数量读取均在收到正文前超时，`request_outcome=unknown`。没有把超时解释成错误数量0、无故障、STOP 已确认或设备内容未改变，也没有读取到异常 PC、故障指令或错误类别。用户看到的 ERR 红灯属于人工现象证据，不能自动生成设备故障码。

## 冷启后的通道检查与所有权交接

08:39:57的原生文件检查报告为 `.plcidf/native-coldplug-file-health-20261019T083957Z/01-application-userprog.foid.json`，只有一条 op1 只读打开请求。`stage=send-read-request`、`out_rc=-7`、`out_transferred=0`、`read_calls=[]`；这是发送阶段超时，与先前收到完整 OUT 后等待 IN 超时的情形分开记录。该会话没有 RUN、应用写入、删除或故障清除。

随后统筹将设备从 WSL detach：`ownership-handoff.json`记录 detach退出码0；紧接的首次 unbind 因枚举暂时查不到 BUSID `7-2` 退出码1。统筹另外报告单独 unbind 命令被管理员权限要求拒绝，没有解除 Shared；该独立命令输出原件未提供给本次文档整理，摘要注明其来源为统筹转述。Windows intent记录 `ClientIPAddress=null`、持久共享标识仍存在，即 **Shared、未 Attached 到 WSL**，不能写成已经 Not shared。

Windows检查为根代理单独监督的固定只读 GCM helper，记录在 `.plcidf/windows-fault-recovery-20261019T084031Z/windows-gcm-intent.json` 和 `windows-gcm-result.json`。它使用原厂 libusb0，接口0 claim成功，固定请求 `120001011d7b00000100000000ff01000000` 发送18字节，单次 IN 返回 `-116` 超时，release与close均为0。外层进程退出码为0，内层结果明确 `ok=false`，没有收到 GCM 正文，也没有重发请求。

这次私有恢复诊断没有经过公开 Python worker 的 Not-shared入口，不能提升为该入口的验收结果，也不能把 Windows读取记录算作纯 Linux能力。所有权交接、原生文件检查和Windows固定读取均未发送 RUN、新应用下载或故障清除；原始恢复包尚未执行。初次解析失败、RUN不一致及各通道失败记录全部保留。

## 定位线索与恢复状态

[研究40](40-unaligned-external-memory-2026-10-19.md)撤销了旧 adapter 对外部 REAL 的未验证 align4 假设，发现旧对象通过外部地址执行 VFP 访存；参考 loader 将既有位地址映射到可能非4字节对齐的字节偏移。这是需要修正的具体风险。真实固件页基址、异常指令和错误码仍未知，故这里只将它记录为离线假说和修正，不把修正版对象或主机测试称作故障已经排除。

已从本次下装前的新鲜读回准备17文件精确恢复包，共 `133913` 字节，manifest SHA-256 为 `c1ef6bd3befe56928e856000b80ed31e191df96281699d05b8b23192a91b1a3a`；原始文件、协议数据和早先好机备份逐字一致。原源码与 build 来源未知并记 `null`，HCPP 未操作，未重算 CRC。恢复包准备不代表已向设备恢复；截至本报告证据截止点，恢复执行与恢复后验收尚无结果。后续结果应明确关联新的连接身份、会话和候选，并另记进展。
