# ADR-0004：厂商自动重编译下的构建意图与部署候选

日期：2026-10-18。状态：已实现软件合同，本机编译及确认前快照已复核；端侧精确字节绑定未实现。

## 问题

Easy521 的 F8 下载和独立程序比较可能重新生成 ARM 对象。将选定构建的清单改成后来的哈希，会丢失用户原本选择的内容；一律只报“文件变了”，又无法解释哪些文件在哪个阶段发生变化。

2026-10-18 实测进一步定位：完整 F7 编译后，打开 F8 设置但不确认，覆盖顶层、STTemp、Temp、PLC 的 108 个文件均未变化。没有新 F8 编译日志。因此不能将旧 F7 结果当作下载确认前的新编译。旧清单还漏掉了 PLC 子目录中的 5 个候选文件，现将构建输入改为完整目录覆盖，保持已有生成目录和锁定工程归档的明确排除。

## 决定

保留四类独立记录，不用新哈希覆盖旧记录：

| 记录 | 证明的事实 | 不能推出的事实 |
|---|---|---|
| verified build / intent | 用户选择的编译结果、源和变量/配置的完整输入、目标和原构建哈希 | 这些字节已进入设备 |
| prepared release | 下载确认前的本地候选、副本哈希、原 intent 和编译转换 | 确认后厂商一定使用这些候选 |
| vendor result / project consistency | 当次厂商完成结果、独立程序比较与当时工程来源 | 精确设备字节或 CPU 正在扫描 |
| binary consistency / runtime | 分别需要设备字节绑定/读回以及实际运行证据 | 不能由前面的记录自动升级 |

`freeze_intent` 拒绝遗漏未知输入的旧清单；调用方应重新构建，不能在部署时临时将额外文件认作旧构建的输入。完整输入中的未知文件仍被绑定，不擅自把 `PLC/` 或 `steps.dat` 归为可忽略缓存。

确认前候选未变化时，release 转换为 `unchanged-pre-confirm`，关联原 verified F7，`compile=null`。确实发生变化时，只有新鲜、独立、带时间窗的零错误编译记录和完整新 ARM 产物才能支持 `vendor-f8-recompile`；缺证据在确认前拒绝。两个分支都把候选复制到独占 UUID 目录，只写一次并保存 release.json，后续复核副本及来源。

下载确认只调用一次。确认后原始输入、候选或证据变化时，保留 release 和厂商终态，返回 unknown，不自动重放。比较命令再次编译时，不能改写原 release；最多分别报告工程一致与字节绑定未核验。当前没有可靠的端侧字节绑定接口，因此生产新路径仍不报告精确二进制部署完成。

## 实现与验证

- `native_autoshop.py`：完整目录输入清单；嵌套候选改变使原构建失效。
- `native_release.py`：intent、编译基线、不可变候选、副本/来源及转换复核。
- `native_deploy.py` / `autoshop_vendor.py`：绑定完整构建记录与单次动作，分别输出 project/binary 验证等级。
- 测试覆盖源/配置/嵌套文件漂移、陈旧或错误编译日志、不完整产物、篡改副本/记录、比较重编译、超时和不重放。

本机真实验证见 [`complete-local-release-root-acceptance.json`](../../evidence/easy521-application-20261018/complete-local-release-root-acceptance.json)：80 项输入含 5 个 PLC 文件，候选捕获和复核通过，设备字节绑定明确 unverified。实际字节副本留在本机，公开仓库只保留来源、清单和哈希。两次 F8 设置均已取消，本轮没有下载确认、RUN 或 STOP。

## 后续

要完成精确部署绑定，还需校准确认后重编译/链接/包装与传输使用的文件，或取得可信的独立字节读回接口。普通正文到 ARM `.o` 的无 GUI 工具链是另一条编译能力，不自动满足本决策中的设备部署条件。
