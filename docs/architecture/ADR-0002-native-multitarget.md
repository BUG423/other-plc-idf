# ADR-0002：原生终端工具链与多目标 PLC 后端

日期：2026-10-17。状态：统筹已采纳，目标模型与开放后端已有部分实现。适用范围：用户提出的“去掉 Windows AutoShop、深入设备内部、支持多种 PLC”。初次形成 ADR 时只做仓库与公开源码调研；随后用户确认三路线并行、路线 2 优先，已取得下述实现结果。完整统一接口、远程板卡与 Easy521 原生兼容仍待验收。

> 同日实施更新：路线 2 的第一个受限本地后端已实现并实测，使用固定 MatIEC、GCC 和真实扫描运行器，见[开放 Linux ST 后端](OPEN_LINUX_RUNTIME.md)。它实现本地构建/部署/运行/停止/观测，不等同于完整通用接口、Beremiz 运行时或 Easy521 固件兼容。本文第 3 节是本轮迁移前的耦合点审计；最终已交付的 CLI、schema 和能力矩阵以最新源码及进展记录为准。

## 1. 决策与用户价值

PLC-IDF 的产品目标应是：AI 在 WSL 中编辑可审查的文本工程，调用统一命令完成检查、构建、部署、启动和运行观测；用户能知道实际采用的编译器、运行时、目标设备和验证级别。Easy521 是第一个兼容目标，后端架构必须允许增加其他厂商 PLC，以及运行开放运行时的自控硬件。

采用两条独立交付、共享工程模型的路线：

1. **厂商兼容后端**保留 PLC 原有固件和运行时，研究 Linux 原生编译器、应用 ABI、应用包与编程协议，使 WSL 直接生成并部署它接受的应用。现有 AutoShop 桥接留作行为对照与回退路径。该路线通过不等于已替换设备固件。
2. **开放运行时后端**首先在我们控制安装与恢复方式的 Linux 目标上，固定一个开放编译器和运行时，实现完全不依赖 Windows 的真实 ST 执行闭环。后续再为有公开资料的 MCU、RTOS 或工业控制板增加 BSP/I/O 驱动。该路线通过不等于 Easy521 已接受开放运行时。

Easy521 更换内核或整套固件是第三层研究目标，必须以确切硬件、启动、驱动和恢复证据为前提，不能作为第一条路线的默认实现方式。

## 2. 从芯片到控制之间缺少哪些环节

“知道芯片是什么”只解决了处理器指令集和部分工具链选择。完整控制路径还包括：

| 层次 | 必须明确的内容 | 不充分的证据 |
|---|---|---|
| CPU/SoC | 精确料号、架构、浮点 ABI、内存及存储 | ARM ELF 属性不能证明 SoC 料号或 Linux 版本 |
| 启动与 BSP | 启动来源、bootloader、内存初始化、设备树/板级初始化、时钟、中断、驱动 | 相同 SoC 的开发板系统不能直接当作 PLC 固件 |
| I/O 硬件 | 隔离电路、输出类型、I/O 协处理器/FPGA、总线、看门狗、掉电行为 | 能执行 Linux 用户进程不能证明能正确读写端子 |
| 运行时 | 扫描周期、任务调度、输入映像、输出提交、保持变量、故障处理 | Linux 或高优先级线程本身不能证明实时性 |
| 应用 ABI/包 | 入口函数、变量布局、厂商库符号、重定位、链接、任务与组态信息、校验 | 同为 ARM 的 `.o` 不代表可被既有运行时加载 |
| 部署与调试 | 身份识别、会话、分块传输、提交、回读、运行状态、在线变量 | Modbus 读写寄存器不是通用 PLC 程序下载接口 |

不同 PLC 可能使用 MCU 裸机、RTOS、Linux，或多个处理器。上层工具链可以共享；下层的设备协议、ABI、实时调度和板级控制必须按已验证目标适配。

一手例子表明不能以“PLC 都是某种 Linux 板”做产品前提：[汇川 AC700](https://www.inovance.com/global/content/details_815_403254.html) 披露 Intel Celeron x86；[Arduino Opta](https://docs.arduino.cc/hardware/opta/) 披露 STM32H747XI Cortex-M7/M4 MCU。这里只比较公开处理器信息，不据此评价任何目标的运行时兼容性或工业适用性。

本仓库已有 ARMv7 应用目标文件线索，但尚不足以确认 Easy521 的具体芯片、完整 OS、BSP 和 I/O 驱动。应保留这一证据边界，见[固件可行性复核](../research/firmware/03-feasibility-assessment-2026-10-17.md)。

## 3. 当前源码阻碍多目标扩展的具体位置

这不是从零建设：`project.py` 已有文本工程、有限类型检查和地址映射，`artifacts.py` 已有 SHA-256 记录，已有设备租约、严格证据以及真实 AutoShop MAIN 编译校验。但这些实现仍偏向首个目标。

| 当前实现 | 限制 | 下一步迁移 |
|---|---|---|
| `backends/base.py:OperationRequest` 必填 `windows_project`，并派生 `.hcp` 路径 | Linux 编译器和远程开放运行时也被迫携带 Windows 工程概念 | 请求只持有工程、目标 profile、构建目录；厂商工程放后端私有配置 |
| `artifacts.py:normalize_target()` 强制 BUSID 与 VID:PID，构建目标等同部署设备 | 无法表达 TCP/SSH/开放运行时目标；设备插口变化会改变构建绑定 | v2 分离编译兼容目标、设备实例、传输定位；旧 v1 保持严格解析 |
| `project.py:PROFILE`、脚手架和 D700/D701 模板固定 Easy521 | 其离线 checker 是 LiteST 小子集，不能充当通用 ST 编译器 | 保留 v1 profile；新增目标中立工程 schema 和显式方言能力声明 |
| `cli.py` 直接选择 `NativeAutoShop` 或旧桥接类 | 新增厂商会不断增加 CLI 特判 | 后端注册表按构建/部署/运行时/观测分别选择，并在执行前协商能力 |
| Modbus 监测脚本绑定 Easy521 寄存器契约 | 内存寄存器值不能证明加载了特定程序或任务正在扫描 | 共享观测记录，保留目标专属映射；程序身份与扫描证据另取运行时接口 |

迁移不应放宽现有设备匹配检查以“兼容所有设备”。应新增带判别字段的 v2 schema、明确转换和拒绝规则，再逐个后端接入。

## 4. 共享工程模型及接口边界

### 4.1 先做受限工程中间表示

第一阶段的 IR 指**工程语义模型**，不是重写一套 ST 编译器或统一所有厂商 AST。源码仍以 ST 为主，声明、任务、I/O 和目标能力采用结构化清单。PLCopen XML 可作为导入/导出格式，但导入成功不能推断所有厂商扩展和运行语义均兼容。

工程模型至少包含：

- **类型与符号**：BOOL、固定宽度有/无符号整数、REAL32 的范围与初值；溢出、类型转换、实数舍入等不一致语义在 profile 中声明。计时器、功能块、数组、保持变量按能力增量开放。
- **程序与任务**：POU、入口、周期、优先级、看门狗预算、共享数据规则；未支持多任务的后端必须拒绝，不能静默丢弃。
- **逻辑 I/O**：应用使用 `motor_enable` 等逻辑点位；目标映射描述通道、方向、物理类型、缩放、故障值和更新阶段。D700、GPIO 17、EtherCAT PDO 是不同目标绑定，不直接写入通用逻辑。
- **兼容目标**：厂商/型号范围、硬件修订、CPU/ABI、运行时及固件版本、编译器版本、BSP/profile 版本。未确认项显式标记未知。
- **构建产物**：源码/生成配置/工具依赖哈希、编译器诊断、ABI 描述、应用包、符号与变量映射；“构建通过”必须说明对应哪一层工具。

不把 Python 自动转换成任意 PLC 程序作为前置条件。AI 先生成受限、可检查的 ST 与工程声明，比隐藏语义差异更容易验证。

### 4.2 接口职责

以下是待实现的契约，不是现有 API 名称：

| 接口 | 输入/输出与职责 | 不承担的责任 |
|---|---|---|
| `TargetProfile` | 兼容性约束、方言、数据类型、任务、I/O、运行时和可用能力 | 不把 USB 插口当成唯一设备身份 |
| `CompilerBackend` | 工程+profile → 诊断、可追溯 BuildBundle | 不默认连接设备，也不默认下载 |
| `Transport` | 在指定端点上建立认证会话和收发边界清晰的数据 | TCP、USB、串口、SSH 本身不定义 PLC 应用部署语义 |
| `DeploymentBackend` | 识别实例、备份/恢复、验证包、传输、提交、验证所加载应用 | 不因发送成功或连接恢复就报告部署验证通过 |
| `RuntimeBackend` | 当前程序身份、状态、启动/停止、任务和符号观测 | 不把 Modbus TCP 可读等同 RUN 或正确程序 |
| `I/O Provider / BSP` | 输入快照、输出提交、看门狗、故障状态、保持存储 | 不向上暴露未版本化的板级寄存器操作 |
| `EvidenceStore` | 每一层的输入、时间、设备观察身份、动作、结果和验证方法 | 哈希证明记录与字节一致，不证明物理设备接受或执行 |

同一设备可采用组合后端：Linux 编译器 + USB 厂商部署 + Modbus 数据观测；组合时必须分别说明编译、下载、程序身份与数据质量的证据。`flash` 应拆分含义：应用部署与固件/BSP 安装分别规划、分别验收，不能复用模糊“烧录成功”。

能力至少区分 `unsupported / declared / observed / verified`，并附版本、时间和依据。`verified` 必须限定到动作与目标版本，例如“Easy521 6.11.0.1 USB 应用下载已验证”，不能泛化成“汇川全系列支持”。

## 6. 有限研究任务与进入下一阶段的门槛

下列工作量是初次研究上限，不是成功承诺。达到上限仍缺关键证据时，提交已知事实、剩余未知和成本，再决定是否继续；不无限投入某一私有目标。

| 任务 | 首轮上限 | 交付物 | 继续/停止门槛 |
|---|---|---|---|
| N1 目标与接口模型 | 1–2 人日 | v2 schema、能力矩阵、Easy521/Open Linux 两份 profile、v1 迁移方案 | 两种目标不再强制携带 Windows 路径/USB 身份；不支持能力能明确拒绝 |
| N2 Easy521 ABI 基线 | 2–3 人日 | 已授权工程的最小差分构建集、符号/重定位/包结构说明、工具版本哈希 | 至少能解释常量/变量/程序结构变更影响哪些产物；无法解释外部符号和包校验时不声称可独立编译 |
| N3 编程协议基线 | 2–3 人日 | 自有设备的官方客户端只读识别/上载会话证据、最小解析器、状态机 | 原生客户端能稳定识别设备并读取非敏感状态，明确会话和校验；未具备身份及恢复条件不进入新客户端应用写入 |
| N4 开放 ST 闭环 | 2–3 人日 | 固定版本环境、最小 ST 工程、真实编译/部署/启动/变量追踪记录 | Windows 和 AutoShop 均未参与；真实执行 ST；故意错误源码失败；观察到属于本次程序的变化 |
| N5 双目标共同语义 | 1–2 人日 | 同一逻辑的逐扫描输入/输出向量、类型边界与计时行为说明 | 两后端在声明子集内结果相符；差异明确拒绝或列为目标限制，不能静默降级 |
| N6 板级移植调查 | 条件满足后另估 | SoC/启动/BSP/I/O/恢复证据表和移植预算 | 缺 I/O 接口、可恢复启动或关键驱动时不进入替换固件；确定型号也不自动通过此门槛 |

N2、N3 只解决兼容路线的一部分。原生 Easy521 应用链必须同时完成代码语义、ABI/包兼容、部署协议及目标执行验证，才能标记“Windows-free Easy521 后端”。仅 DLL 在 Wine 中工作属于兼容环境方案，需要明确标记，不能称为 Linux 原生编译器。

## 7. 两条路线分别验收，再做交叉验收

| 验收项 | Easy521 厂商兼容后端 | 开放运行时后端 |
|---|---|---|
| 文本工程检查 | 当前 LiteST 子集、真实厂商错误反馈 | 同一受限语义模型、开放编译器错误反馈 |
| 编译成功 | 新产物、厂商诊断、源码及工具指纹；以后增加原生等价性 | 实际生成并构建可由固定运行时加载的应用；不能只跑虚拟寄存器从站 |
| 部署成功 | 设备身份、应用包、提交/回读或厂商一致性证据 | 目标运行时身份、包版本、编译结果、加载程序身份 |
| 运行成功 | 当前程序身份 + RUN + 本次程序可解释的扫描进度 | 当前程序身份 + 运行状态 + 本次 ST 变量变化 |
| 时序及输出 | 单独测量实际扫描、超时、STOP/故障输出 | 先软 PLC 功能验收，再在目标硬件测实时调度、I/O 延迟和故障行为 |
| Windows-free | 整个成功链中不调用 Windows 二进制或服务 | 整个成功链同样检查；在普通 Linux 上通过只证明该目标 |

共同基准先选择无物理输出的计数器、布尔逻辑、限幅和类型边界，再增加计时器、保持与实际隔离 I/O。相同寄存器值不是跨目标语义等价证明；记录必须绑定本次源码、运行时、设备和观测方法。开放后端完成与 Easy521 研究受阻可以同时如实报告，不用一种结果替代另一种。

## 8. 暂不采纳的路线

- 先做一个“适用于所有 PLC”的固件镜像：硬件、I/O 与启动差异使该承诺无法验证。
- 因 Modbus 可读就实现“通用下载器”：数据协议与应用部署不是同一契约。
- 先重写完整 ST 编译器：当前最大的缺口是目标 ABI、包和部署证据，复用开放工具链更快获得可验证闭环。
- 以逆向所有厂商为扩展策略：先通过一个厂商兼容目标和一个开放运行时目标验证接口，再按明确的型号/版本支持矩阵逐项扩展。
