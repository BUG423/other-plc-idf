项目已经具备 CLI 编排原型、固定寄存器契约的 Modbus 数采和虚拟从站演示。尚未验收“AI 修改用户 ST → 同步工程 → 厂商编译 → 可识别产物 → 指定 PLC 部署 → 程序校验 → 运行反馈”的完整链路。设计中的命令、接口和门禁不能按已实现功能汇报。

## 1. 从第一性原理明确需求

用户要把描述、改码、构建、部署和反馈放到 WSL 中同一个 AI 对话工作流里。核心收益是减少人工搬运工程与重复点击，并让每次反馈都能对应到确切的源代码、产物和设备。Windows 是否参与执行是后端选择；它必须在能力与环境报告里如实呈现。

完整闭环应处理五类对象：

1. **可审查的文本工程**：ST、变量、任务配置、I/O 地址、初值、保持区、依赖和工具版本。不能仅有一段正文而缺少厂商工程语义。
2. **编译结果**：输入版本、目标型号、编译器版本、结构化诊断、产物与哈希。发出 F7 不证明编译成功。
3. **部署事务**：指定设备、指定产物、授权对象、设备所有权、执行状态和程序一致性校验。发出 F8/ENTER 不证明程序已正确下载。
4. **运行观测**：带原始值、契约版本、字序、时间和质量标记的数据，以及可信来源的任务/故障状态。固定寄存器读取不等于任意程序调试。
5. **系统固件与运行时**：内核、引导、驱动、PLC 扫描调度、I/O、看门狗、保持数据和现场总线。这与用户应用开发属于不同研究对象。

建议用以下可验收表述描述需求：开发者在 WSL 编辑一个明确目标的文本工程，AI 能运行检查和构建、定位真实错误；部署前得到绑定产物与设备的计划，经授权部署并完成一致性校验；随后读取对应工程定义的变量与状态，能把失败反馈到下一轮修改。每个阶段允许失败或能力不可用，禁止用后续演示数据掩盖前一阶段尚未执行。

ST 是首期合理选择：已有源文件、CSV 和人工导入路径可复用。它不是唯一可文本化或由 AI 使用的 PLC 语言；图形语言的序列化、生成和语义比较需要单独的工具链验证，首期不承担即可。

## 2. ESP-IDF 对标的实际范围

| 体验维度 | PLC-IDF 应交付的对应能力 | 当前差距 |
|---|---|---|
| 项目创建 | 独立示例、版本化 manifest、源文件、变量和任务配置 | `init/new` 未实现，主要依赖已有 BESS 工程 |
| 环境配置 | `doctor`、目标和工具版本识别、依赖声明 | 没有能力自检；仓库路径和本机 Windows 路径耦合 |
| 编译 | 真实诊断、产物清单和可追溯输入 | 有 GUI 计划；成功判据及产物验证未完成 |
| 下载 | 绑定设备与产物、授权、独占、下载和程序校验 | 有 GUI 下载动作路径，缺少完整事务与验收 |
| monitor | 对应工程的变量、状态、故障和质量标记 | 固定 D0–D17 数采；真机网口待验；不是通用调试器 |
| 离线测试 | 检查与场景回归分别标识；厂商模拟器作语义对照 | 虚拟从站播放简化规则，不执行用户 ST |
| 可重复交付 | 独立安装、版本锁定、CI、构建与证据关联 | 可编辑安装可用，不代表 wheel 在仓库外完整可用 |
| AI 接入 | 全命令机器输出、稳定退出码、计划与执行分离 | 只有部分输出可机读；当前 CLI 退出码不同于设计 |

三个动词对齐表达了产品方向；成熟度应按上表验收。Windows 无头调用、Windows GUI 自动化、Linux 原生编译是三个不同能力，不能混称“原生”。

## 3. 需求—实现—验收追溯矩阵

状态定义：**已有**指源码存在相应能力，不自动代表真机已验收；**部分**指只覆盖需求的一部分；**未实现**指目标接口或机制缺失；**待硬件**指必须补实验机证据。以下为修复前快照，P0 修复的最终结果另见 §4。

| 需求 | 快照状态 | 实现证据与缺口 | 完成判据 |

| FR-L1、AC-13 | 未实现 | [`cli.py`](../../src/plc_idf/cli.py) 仅注册五命令，无 `init/new` | 新建独立工程具备 ST/CSV/配置；检查通过；厂商打开验收另列 |

非功能需求也存在实施缺口：

| 需求 | 现状与验收重点 |
|---|---|
| NFR-SEC1~4 | monitor 只读已具备；桥式事务、证据持久性、不可判别字序和不确定状态尚不满足设计的失败封闭要求 |
| NFR-REL1~5 | 有 subprocess 超时和回收；写动作不应使用读操作的重试策略；退出码当前为 0/1/2 等透传，不是 SPEC 的 0/2/3/4/5/6 |
| NFR-PORT | [`pyproject.toml`](../../pyproject.toml) 的 dependencies 为空，wsl-tools 未作为包资产分发；[`config.py`](../../src/plc_idf/config.py) 按仓库相邻目录找脚本。必须验收从 wheel 安装后在仓库外执行 |

## 4. P0 缺陷与当日修复边界

以下缺陷记录的是修复前行为。strict bool、GUI 动作不重试及未校验不报成功三项修复已落地并通过软件集成验证，结果见 [进展记录](../management/PROGRESS.md)。软件测试不能证明真实厂商编译或下载校验已实现；未覆盖的部署事务、设备租约与证据缺口仍待处理。

| 问题 | 修复前证据 | 当日修复/剩余验收 |
|---|---|---|
| 非布尔配置被当作启用 | `check_bridge_authorization()` 使用 `bool(cfg.bridge.get(...))`，字符串 `"false"` 为真 | 已修为仅显式布尔 true 启用；负向软件测试见进展记录 |
| 未验证结果仍报成功 | `_execute()` 跳过空命令 verify，最后只要子进程返回成功就返回 `BackendResult(True, ...)` | 已改为未校验不报成功；真实产物、诊断和下载一致性校验仍未实现 |
| GUI 写动作盲重试 | bridge 使用默认 `retryable=True`，F8/ENTER 可能在超时后重复执行 | 已禁止 GUI 动作自动重试；相关回归通过，不代表真机动作获准执行 |
| 成功语义缺失 | inspect 不验证工程名，diagnostics 不解析为结论，下载后程序校验未实现 | 保守失败只能阻止误报，不能宣称已实现真实编译/下载校验；另开能力任务 |
| 部署与对象未绑定 | 缺产物哈希、型号匹配、目标身份和一次性计划 | 不在前三项小修复的完成范围；完成前不得把真机部署报告为企业可用 |
| 设备并发缺少互斥 | bridge 校验一次 USB 归属，不持独占租约 | 租约、冲突和中断恢复需单独实现 |
| 证据写失败后继续 | EvidenceLogger 捕获 OSError，只警告 | 新副作用事前须保证证据通道可写；动作已发生后写失败应记录不确定状态，不能盲目回滚或重试 |

当日修复针对已发现的误放行、重复动作和成功误报补上软件防线；它不等价于厂商编译器适配、真实下载或固件研究完成。

## 5. 文档与证据的勘误规则

本次已在 SPEC/ARCH 中增加实现边界，并纠正以下主要断言；历史 `docs/wsl-feasibility/` 和原始探测文件保留不改。

- “未找到公开实现”应带检索范围和日期，不能写成“全网零实现”或“不可能原生编译”。
- 15 组 USB RTU 静默记录证明的是这些条件下无响应；足以暂不支持该路径，但不是穷尽协议证明。
- 命名与三个命令对齐不能证明功能等价；架构中的 Protocol、注册表、租约和授权字段仍需落地。
- “虚拟闭环”仅指当前进程和数采链；用户 ST、Python 算法镜像和厂商模拟器语义验收应分开标识。
- RS485 在旧 SPEC/ARCH 中仍写本体有无 TBD，而 [手册复核](../research/firmware/01-manual-facts.md) 已记录本体 1 路及端子页码；本次已更新文档，实物接线与通信参数验收仍未完成。
- FR-M3 “不可判别回落 ABCD”与 NFR-SEC4 失败封闭冲突。建议保留原始字、质量标记为未确认，并要求显式字序；在实现前统一需求判据。
- SPEC 用例 UC-02 将编译纳入授权，而 ARCH 时序和策略表允许编译仅留证据；应明确区分本地/Windows 工程副作用与 PLC 写操作，再统一规则。
- 固件研究档案把“升级过程抓包”描述为零变砖风险不准确：采集是被动的，但触发固件升级仍在写系统。未查到漏洞公告不证明没有漏洞或研究；通用 FEL 能力也不证明本机入口、安全启动状态或恢复能力。

## 6. 固件研究与主线应用开发的关系

[底层可行性复核](../research/firmware/03-feasibility-assessment-2026-10-17.md) 记录现有 `STTemp/MAIN.o`、`Temp/stprog.o` 为 ARMv7-A/ELF 等中间产物线索。该线索有助于研究目标代码、符号与调用接口；不能据此推定具体 SoC、完整系统镜像、启动权限、可用 BSP 或可直接部署的应用格式。本报告不另作硬件型号判断。

应分别建立三条研究任务：

1. **原生应用编译**：检查实际编译产物、符号、重定位、依赖与调用约定；明确方言和运行时入口，先在离线样本中与厂商产物对照。
2. **应用下载协议**：在取得合法样本后离线分析正常连接、读状态和下载会话；协议掌握不代表应用产物兼容。
3. **系统固件/运行时**：核验官方文件来源、机型和版本、哈希、格式及系统组成；拿到 Linux 内核源码不等于恢复 PLC 控制栈。

研究可以与工程主线并行；主线验收不依赖更换系统固件。任何真实设备实验需与离线分析区别安排，当前报告没有授权烧录、探测调试口或改变设备状态。

## 8. 进展汇报与 GitHub 同步口径

每个工作包至少记录：负责人角色、状态、依赖、变更、验收命令/结果、证据路径、剩余问题。状态建议为 `planned / in_progress / in_review / verified / needs_input`；没有运行验证或缺硬件证据时不能标 `verified`。

GitHub issue 的关闭条件对应本报告的验收判据。工作开始、里程碑完成、发现重大偏差或依赖变化时同步状态；向用户汇报应说明已经证明什么、尚缺什么和下一步能解决什么。后续定时自动工作还取决于实际调度能力，不能仅靠文档声称已安排。

本报告未创建 GitHub 任务或自动化调度；这些由统筹代理在本次授权范围内统一执行并报告结果。
